# 交給複審 / 老闆：Chatseek 1.2.0 Gemini

分支 `feat/gemini`，已複審並合進 main（複審修正見下方「複審後」）。開發機沒有登入任何 Google 帳號。費用 $0，沒有呼叫付費服務。

這版接在已經合進 main 的 1.1.0（`724dbd7`，共用最後活動時間和收錄健康檢查）上面。Gemini 只登記自己的網站、側欄順序和健康檢查，不再自備 `exact` / `estimated` / `unknown`。

## 改了什麼

- 第四家：gemini.google.com。側欄清單、目前這則對話的訊息、搜尋、只篩 Gemini。
- 只讀頁面上已經畫出來的內容。沒有 fetch / XHR，沒有 API Key，沒有打 Gemini 內部介面。
- 權限只加 `https://gemini.google.com/*`。www.google.com、aistudio、bard、mail、accounts，以及 Perplexity、DeepSeek，驗證腳本仍會拒絕。
- 多帳號網址保留 `/u/N/`。這則頁面自己的路徑優先（所以 `/u/4/gem/...` 不會被改成預設帳號）。側欄連結如果沒寫帳號，就沿用目前這個分頁的 `/u/N/`。兩邊都沒有時，存成 `/app/<id>`，點回去可能開到預設帳號。
- `/share/`、沒有 id 的 `/app`、Gem 編輯頁不收。
- 圖示仍是 1.1.0 的方向 D（深色圓角底上的符文）。這版沒有換標。
- 日期跟 ChatGPT / Claude / Grok 同一套，文案在 `src/activity-time.js`：
  - 這一列有 `time[datetime]` 或時間屬性：`page-exact`，畫面上是普通的最後活動時間，不加「約」。
  - 沒有精確時間，但側欄裡至少有一則已經有精確時間或分組時間：按上新下舊插值，來源是 `sidebar-rank`。繁體顯示「約」，簡體顯示「约」。
  - 你在開著的 Gemini 分頁裡送出新訊息（對話尾端多出一則）：這則對話記成 `observed`，時間是當下，不加「約」。之後側欄其他列以它為錨點插值，顯示「約」／「约」。只是打開舊對話、往上捲出更早的訊息，都不算活動。
  - 整欄都沒有那種錨點：來源留在 `first-seen`。繁體是「日期未知（收錄於 …）」，簡體是「日期未知（收录于 …）」。括號是收進索引的時間，不是活動時間。排序仍跟側欄，越上面越新，但不會把每一則都標成「約」，也不會整欄顯示「剛剛」。
- 比較準的時間不會被比較鬆的蓋掉。
- 打開的對話頁如果一則訊息都沒讀到，大約 8 秒後仍是 0，側欄底部會提示，工具欄角標是 `!`。繁體像是「Gemini 頁面可能改版，請回報（最後收錄 hh:mm，0 則訊息）」。有讀到訊息時，底部是「Gemini：最後收錄 hh:mm，N 則訊息」。控制台只打選擇器名字，不打正文。沒有 id 的頁面、分享頁，不會被當成這次失敗。

## 怎麼測（自動化）

在倉庫目錄：

```bash
npm run verify
npm run test:search
npm run test:fixture
npm run test:gemini
```

`test:search` 含 IndexedDB 1 → 2 的升級測試。`test:fixture` 跑 ChatGPT 和兩個 Gemini 測試。`gemini-capture-test` 把 Gemini 內容腳本接到真的 `background.js` 和 IndexedDB：第一次只有「日期未知」但保持側欄順序，往上捲不算活動，送出新訊息變 `observed`、旁邊幾列變「約」，串流中的回覆只算一則。`test:gemini` 用離線 HTML，不登入。它檢查：使用者 / Gemini 角色和順序、思考過程、「You said / 你說了 / Gemini 說了」、按鈕、輸入框都沒被收進去，分享頁和沒有 id 的 `/app` 會被跳過，以及日期是接到共用的 `page-exact` / `sidebar-rank` / `first-seen`，不是 Gemini 自己估的時間。

## 老闆在自己電腦上怎麼測

開發機不能登入 Google。請在自己的 Chrome、自己的帳號上做。不用另外付費。

1. 拿到這個分支的資料夾。打開 `chrome://extensions`，打開開發者模式。
2. 如果已經裝過 Chatseek，點「重新載入」。沒裝過就點「載入未封裝項目」，選這個資料夾。版本應是 **1.2.0**。工具欄圖示是方向 D 的符文，不是舊標。
3. 把已經開著的 gemini.google.com 分頁重新整理一次。擴充重新載入不會自動換掉舊分頁裡的腳本。ChatGPT / Claude / Grok 的分頁也要重新整理一次，才會用 1.1.0 之後的內容腳本。
4. 在 Gemini 打開至少 3 段舊對話（點進每一段，讓正文畫出來）。臨時對話、或關掉活動記錄所以網址沒有 id 的，本來就不會收。
5. 打開 Chatseek 側欄，搜其中一段裡很少見的詞。應該命中那一段，標籤是 Gemini。點那一列，應開回原來的對話（多帳號的話，網址裡最好還看得到 `/u/N/`）。
6. 搜一個顯然不存在的詞，應顯示沒有符合。
7. 關掉側欄再打開，或到擴充頁面重新載入擴充再開側欄。剛才的索引還在。網站分頁要再重新整理，才會繼續收新內容。
8. 只打開舊對話、還沒在 Gemini 裡送出任何新訊息時：日期不該整欄空白，也不該是「剛剛」。Gemini 側欄沒有時間，所以每一則都是「日期未知（收錄於 …）」（簡體介面是「日期未知（收录于 …）」）。順序跟 Gemini 側欄一樣，越上面越新；你點開過的那幾則不應掉到最底。在「全部」裡，這些 Gemini 列排在有日期的 ChatGPT / Claude / Grok 下面。
   - 再打開一則舊對話，什麼都不送，等 10 秒以上：它仍是「日期未知」，不能變成「剛剛」。如果變了，請截圖回報，這是誤判。
9. 在其中一則舊對話裡送出一句新訊息，等 Gemini 回完：這則跳到 Chatseek 的 Gemini 最上面，時間是「剛剛」或「N 分鐘前」，**沒有**「約」。同一個 Gemini 側欄裡的其他列變成「約 …」／「约 …」，滑鼠停上去寫「推估：依側欄順序」。這則下面的列只知道「比它舊」，目前共用規則每往下一列多算一小時，所以「約 3 小時前」只代表順序，不代表真的是三小時前。重新整理頁面、重新載入擴充之後，這則的時間和順序還在。
   - 新開的對話（從沒有 id 的 `/app` 開始）第一輪問答通常還是「日期未知」；在同一則再送第二句才會有精確時間。
10. 篩選按「Gemini」只剩 Gemini；按「全部」會跟 ChatGPT、Claude、Grok 混在一起。
11. 如果某段網址是 `/app/<id>`（或 `/gem/.../<id>`）的對話，正文明明在畫面上，等大約 8–10 秒仍搜不到正文：側欄底部要出現 Gemini 的改版提示，工具欄角標是 `!`。瀏覽器主控台那一行只有選擇器名字和「0 messages」，沒有對話正文。沒有 id 的新對話、`/app/download` 這類設定或下載頁不該觸發這個提示。
12. 開一則 Gemini 臨時對話聊一句：它不應出現在 Chatseek 裡。開發時沒看過真頁面的臨時對話網址；如果它被收了，請把網址形狀回報。

## 已知限制

- 沒在這個分頁打開、也沒出現在側欄裡的舊對話，仍然搜不到。這次不做「一次收完全部歷史」，也不匯入 Google Takeout。
- 很長的對話只索引已經畫出來的訊息。要多收，就在那則對話裡往上捲。
- Gemini 側欄和對話頁都沒有真實修改時間，唯一不靠網路的錨點是「在開著的分頁裡看到新訊息」。沒有這種錨點時畫面上是「日期未知」，不是「約」。這是 1.1.0 的共用規則，不是 Gemini 壞掉。
- 錨點以下的列，共用插值每列減一小時，只保證順序。要改成例如「早於 <錨點日期>」需要改 `src/activity-time.js`，會一起影響 ChatGPT / Claude / Grok，這版沒有動。
- Gemini 的置頂對話沒有「Pinned」標題時，會被當成最新的幾則參與插值。
- 假設側欄是上新下舊。如果 Gemini 改成別的排序，估計和未知日期的排序會跟著錯，但不會假裝那是精確時間。
- 沒有 `/u/N/` 的網址，點回去可能開到預設帳號。
- 不收 `/share/`、不收沒有 id 的新對話、不收 Gem 編輯頁。Canvas / 圖片沒有另外做；訊息裡的文字如果在正文節點裡，會順便收。
- 選擇器是依公開的開源專案寫的，開發時沒看過登入後的真頁面。第一次實機如果收不到，優先檢查下面幾項。
- 地區要能打開 gemini.google.com，這跟擴充無關。

## 最可能壞掉的選擇器

1. 側欄列：`[data-test-id="conversation"]`，對話 id 在 `jslog` 的 `c_<id>`。其次才是 `a[href*="/app/"]`。
2. 網址形狀：`/app/<id>`、`/u/N/app/<id>`、`/gem/<gemId>/<id>`。id 要求 8 到 128 個英數、底線或減號，並且含數字或是 12 位以上的十六進位，所以 `/app/download` 不算對話。
3. 使用者訊息：`user-query`、`.user-query`、`.query-text`。
4. Gemini 回覆：`model-response`、`message-content`、`.markdown`、`.model-response-text`。
5. 要排除的思考過程：`model-thoughts`、`.thoughts-container`。
6. 螢幕閱讀器標籤：`.cdk-visually-hidden`（You said、你說了、Gemini 說了）。
7. 輸入框：`.ql-editor`。
8. 訊息 id：優先用 `.conversation-container[id]`。找不到時退回正文前 180 字的雜湊；那樣串流中的短回覆可能多存幾則不完整的版本，但不影響搜尋，也不會誤判成活動。

找不到時會安靜跳過，不會對頁面報錯。0 則訊息的對話頁會走上面的健康檢查。

## 複審後（2026-10-08）

- `background.js` 轉給資料庫時漏了 `pageMessageIds` / `captureId`，所以 1.1.0 的 `observed` 在四家平台都沒有真的觸發過（只在單元測試裡直接呼叫 db 時有）。現在會轉，ChatGPT 1.1.0 實機第 6 步「再發一句，跳到最上面、時間變剛剛」也靠這個。
- 看到新訊息之後，同一輪把側欄重寫一次，旁邊幾列馬上以新錨點插值，不用等側欄順序改變。
- 打開的 Gemini 對話寫訊息時帶著側欄名次，單獨一列被重估成「最後一名」，點開過的對話會掉到底。已修。
- `/app/download`、`/app/settings` 這類字詞路徑不再被當成對話，也不會誤報改版。回覆裡貼的 Gemini 連結不再被當成側欄列。列標題去掉 `mat-icon` 的圖示字。
- `verify` 另外擋 `fetch(`、`sendBeacon`、`WebSocket`、`EventSource`、`batchexecute`，以及 `*.google.com`、`<all_urls>`。
